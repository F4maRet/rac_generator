# Генератор рационализаторских предложений (Ф. № БИ-7)

Веб-приложение для подготовки рационализаторских предложений: нейросеть генерирует
наименование и текст 6 разделов по заданной теме, а программа автоматически
собирает готовый **Word-документ (.docx)** по бланку Ф. № БИ-7 — с таблицей
авторов, процентным распределением вознаграждения и всеми подписями.

**Автор и разработчик:** Лаукарт Михаил Сергеевич. В интерфейсе внизу страницы —
подпись автора и кнопка «О программе» (описание, автор, версия).

## Возможности

- Генерация текста через **любое число нейросетей** — не только несколько
  «зашитых» провайдеров, а полноценный список в Настройках: добавляйте,
  редактируйте, включайте/выключайте, помечайте платная/бесплатная и
  проверяйте доступность каждой модели (по одной или все разом кнопкой «Пинг всех»).
- **Автоматическое переключение при исчерпании лимита**: генерация пробует
  включённые модели по очереди (по приоритету), и если у одной закончился
  бесплатный лимит (HTTP 429) или она недоступна — программа сама переходит
  к следующей, пока какая-то не ответит или не закончатся все варианты.
  В интерфейсе видно, какая модель сработала и что было испробовано до неё —
  и в реальном времени, через прогресс-бар этапов (отправка → получение →
  формирование разделов → готово), а не просто «крутилку».
- **Отметка «Лимит»** у каждой модели (в таблице «Настройки» и в выпадающем
  списке на «Новое предложение») — «в норме» / «исчерпан» / «неизвестно».
  Обновляется не только вручную кнопкой «проверить», но и автоматически по
  результатам настоящей генерации — если модель однажды ответила 429, это
  сразу видно всем, без отдельной проверки.
- **Поиск-автодополнение авторов** при выборе 6 соавторов: начинаете вводить
  фамилию — появляются подсказки; либо открываете таблицу кнопкой «☰» с
  поиском и фильтром по каждой колонке. Выбор именно из списка обязателен —
  это исключает ошибку «автор не найден» при сборке документа.
- База авторов с поиском, фильтрами по колонкам и **редактированием** записей
  (не только добавление/удаление).
- Сохранённые адреса API (OpenRouter, Groq, Ollama и свои) с автодополнением —
  начинаете вводить название/адрес в поле «base_url» и выбираете из подсказок,
  не нужно вводить один и тот же адрес заново для каждой новой модели.
- Таблица моделей — с фильтрами по каждой колонке и сортировкой по клику на
  «Приоритет» и «Включена»; «Пинг всех» проверяет только включённые модели.
- Название модели в таблице кликабельно и ведёт на страницу модели на
  openrouter.ai, если адрес указывает на OpenRouter.
- Автоматическая сборка `.docx` строго по вашему шаблону, с сохранением
  форматирования (Times New Roman 10pt, отступ 1,25 см, выключка по ширине,
  одинарный интервал — для текста 6 разделов). Сам шаблон размечен
  плейсхолдерами (`{{SIGN}}`, `{{VICE_HEAD}}`, `{{VICE_FIO}}`, `{{sectionN}}`)
  и не хранит лишних демо-данных, поэтому весит считаные килобайты, а не сотни.
- История сгенерированных предложений (с пометкой, какая модель их написала) —
  можно скачать `.docx` повторно или **удалить** ненужную запись вместе с файлом.
- **Шаблон документа можно менять прямо из интерфейса** (вкладка «Настройки»):
  загрузить свой `.docx`, скачать текущий или вернуть встроенный. Загрузка
  проверяется пробной сборкой документа — несовместимый файл отклоняется с
  объяснением, что именно не так, а не ломает генерацию молча.
- Интерфейс адаптивен под узкие окна браузера: широкие таблицы прокручиваются
  внутри своей карточки, а не ломают вёрстку страницы.

## Запуск через Docker (рекомендуется)

Самый простой способ развернуть и потом обновлять приложение — Docker Compose.
Нужен только установленный Docker.

```bash
cd project
docker compose up -d --build
```

Откройте **http://localhost:8000**. База авторов, история и сгенерированные
`.docx` хранятся в именованном томе `rac-data` — они переживут
`docker compose down`, пересборку образа и обновление кода.

Полезные команды:

```bash
docker compose logs -f        # логи приложения
docker compose down           # остановить (данные в томе сохранятся)
docker compose down -v        # остановить И стереть все данные (осторожно)
docker compose up -d --build  # пересобрать после изменений в коде
```

Порт и число воркеров настраиваются переменными окружения (можно положить в
файл `.env` рядом с `docker-compose.yml`):

```bash
APP_PORT=8080
WEB_CONCURRENCY=4
```

### Защита доступа (аудит 2026-10-03)

**По умолчанию приложение НЕ защищено паролем.** До этого аудита так было
всегда, и именно поэтому любой, кто может достать до порта контейнера (общая
сеть части, проброшенный порт, VPN и т.п.), мог без единой проверки увидеть
персональные данные авторов (ФИО, звание, место службы) и ключи API платных
нейросетей — они отдавались открытым текстом любому, кто откроет страницу.

Чтобы включить простую защиту (HTTP Basic — браузер сам покажет окно
«логин/пароль»), задайте обе переменные в `.env`:

```bash
APP_USERNAME=admin
APP_PASSWORD=замените-на-свой-пароль
```

и пересоберите (`docker compose up -d --build`). Если задана только одна из
двух переменных или не задана ни одна — защита выключена (приложение в этом
случае печатает предупреждение в лог при старте), чтобы обновление кода само
по себе никого не заблокировало неожиданно. `/api/health` всегда доступен без
пароля — иначе сломался бы встроенный `HEALTHCHECK` Docker.

Это не замена полноценной системе ролей/пользователей, но закрывает самый
грубый случай — «порт торчит в сеть без всякого пароля». Ключи API в ответах
`GET /api/models` теперь в любом случае замаскированы (видны только первые/
последние символы) — даже с паролем ключи целиком не отдаются обратно в
браузер, редактирование модели не требует вводить ключ заново, если вы его не меняете.

**Второй аудит (2026-10-03):**

- **Ключ привязан к серверу.** Сохранённый ключ отправляется только на тот
  сервер, для которого его вписали. Если поменять адрес модели на другой
  сервер, программа попросит вписать ключ заново (в форме это видно сразу —
  значок «нужен заново»). Каталог тоже использует сохранённый ключ, только
  если его адрес указывает на тот же сервер. Раньше ключ можно было увести,
  даже не видя его: сменить адрес модели и нажать «проверить», или открыть
  каталог с чужим адресом.
- **Запросы с чужих сайтов запрещены.** Раньше любой сайт, открытый в вашем
  браузере, мог обращаться к программе (CORS был открыт для всех). Интерфейс
  работает на том же адресе, что и сервер, поэтому это разрешение не нужно.
- **Пароль может быть на кириллице.** Раньше с паролем вроде «Пароль2026»
  войти было невозможно в принципе.

### Длительность генерации и устойчивость к обрыву соединения

- Общий перебор моделей и попыток эскалации `max_tokens` в одной генерации
  ограничен переменной `GENERATION_DEADLINE_SECONDS` (по умолчанию 600 — 10
  минут). Раньше потолка не было вовсе, и длинная цепочка из нескольких
  медленных/ошибающихся моделей могла растянуться на десятки минут.
- Сама генерация теперь выполняется в фоновой задаче на сервере, не
  привязанной к жизни HTTP-соединения: если вкладка браузера закрылась или
  страница перезагрузилась посреди долгого перебора моделей, генерация **не
  прерывается** и в итоге сохраняет результат. При следующем открытии
  страницы она сама заберёт готовый результат (или сообщение об ошибке) по
  `request_id`, не начиная генерацию заново и не расходуя лимит нейросетей
  повторно.
- При HTTP 429 (лимит частоты запросов) с заголовком `Retry-After` и коротким
  временем ожидания (до 15 сек) программа один раз подождёт и повторит тот же
  запрос той же модели — такие лимиты обычно снимаются за секунды, и короткая
  пауза экономит дневной лимит следующей модели в цепочке, которую иначе
  пришлось бы расходовать напрасно.
- Одна попытка обращения к модели ждёт ответа до 240 секунд
  (`GENERATION_TIMEOUT_SECONDS`; раньше 90). Шесть разделов на русском — это
  несколько тысяч токенов, и медленная бесплатная модель могла не успеть.
- Если сервер перезапустили посреди генерации, страница через несколько
  минут честно сообщит «генерация прервалась», а не будет показывать «ещё
  выполняется» до 6 часов.
- Дата в документе считается по часовому поясу `APP_TIMEZONE` (по умолчанию
  `Europe/Moscow`), а не по часам контейнера (UTC). Раньше с 00:00 до 03:00
  по Москве в документ попадала вчерашняя дата.

### Масштабирование

- **Внутри одного контейнера**: `WEB_CONCURRENCY` — сколько uvicorn-воркеров
  поднимает gunicorn. Годится, чтобы утилизировать несколько ядер CPU на одной
  машине.
- **Несколько контейнеров/реплик** (например, `docker compose up --scale
  rac-generator=3` за общим балансировщиком, или деплой в Kubernetes): текущее
  хранилище — SQLite-файл в общем томе, он не рассчитан на параллельную запись
  из разных процессов на разных машинах. Для горизонтального масштабирования
  на несколько нод замените `db.py` на подключение к PostgreSQL (структура
  таблиц простая, миграция небольшая) — тогда каждая реплика будет только
  генерировать `.docx` и обращаться к общей БД, что масштабируется без
  ограничений. Само API уже безсостоятельно (stateless) за исключением
  обращений к SQLite/файлам, так что этого одного изменения достаточно.
- В образ встроен `HEALTHCHECK` (`/api/health`) — подходит для readiness/liveness
  проб в любом оркестраторе.

### Проблемы со сборкой образа

Если `docker compose up --build` падает на шаге установки зависимостей с
чем-то вроде:

```
ERROR: Could not find a version that satisfies the requirement fastapi>=0.111 (from versions: none)
ERROR: No matching distribution found for fastapi>=0.111
```

это **не** проблема с `requirements.txt` — `(from versions: none)` означает,
что `pip` вообще не смог получить список версий с индекса пакетов, то есть
у контейнера, в котором идёт сборка, нет доступа к pypi.org. Сам файл
зависимостей тут ни при чём.

Как диагностировать:

```bash
# если это тоже не работает - проблема на уровне Docker/сети, а не проекта
docker run --rm python:3.12-slim pip install --dry-run requests
```

Типичные причины и что делать:

- **Нет интернета у самого Docker** (сеть, VPN, корпоративный прокси) —
  проверьте `docker run --rm alpine ping -c1 pypi.org`. Если не пингуется,
  дело в сети/DNS до Docker, не в проекте.
- **Docker Desktop за прокси** — пропишите прокси в Docker Desktop
  (Settings → Resources → Proxies), а не только в переменных окружения
  хоста: сборка образа идёт внутри демона Docker, он их не наследует
  автоматически.
- **pypi.org недоступен напрямую** (блокировки, нестабильный маршрут) —
  соберите на зеркале, не трогая код: создайте файл `.env` рядом с
  `docker-compose.yml` со строкой

  ```
  PIP_INDEX_URL=https://pypi.org/simple
  ```

  заменив адрес на доступное вам зеркало (например корпоративный Nexus/Artifactory,
  или один из публичных зеркал PyPI), и пересоберите:
  `docker compose up -d --build`.
- **Сбой самого Docker Desktop** — помогает перезапуск или Troubleshoot →
  Reset to factory defaults (сеть у Docker Desktop иногда «залипает» после
  сна ноутбука/смены Wi-Fi).

## Установка и запуск без Docker

```bash
cd project
python3 -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate
pip install -r requirements.txt

cd backend
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

Откройте в браузере: **http://localhost:8000**

При первом запуске автоматически создаётся файл базы данных
`data/app.db` и папка `data/output/` для готовых документов. Расположение
папки с данными можно переопределить переменной окружения `DATA_DIR`.

## Обновление программы

После замены файлов новой версией **обязательно перезапустите сервер**:

- в Docker: `docker compose up -d --build`;
- без Docker: остановите uvicorn (Ctrl+C) и запустите снова; если в новой
  версии появились зависимости, сначала `pip install -r requirements.txt`.

Почему это важно: интерфейс (папка `frontend/`) сервер читает с диска при
каждом запросе, поэтому браузер видит новые кнопки сразу. А свой Python-код
сервер загружает один раз при старте. Без перезапуска новый интерфейс
обращается к старому серверу, и новые функции падают с ошибкой вроде
«Эндпоинт /api/catalog не существует». Начиная с этой версии программа сама
замечает такое расхождение и показывает вверху страницы красное
предупреждение с инструкцией. Версия сервера видна в `GET /api/health`.

## Шаблон документа: почему правки «не применяются» и как это исправлено

Раньше шаблон (`backend/template.docx`) лежал рядом с кодом и **запекался в
Docker-образ** при сборке (`COPY backend/ ./backend/` в `Dockerfile`). Том
(`volumes:` в `docker-compose.yml`) смонтирован только на `/app/data` — сам
код и файлы `backend/` в него не входят. Поэтому если отредактировать
`template.docx` на диске и просто перезапустить контейнер
(`docker compose restart` или `up -d` без `--build`) — контейнер продолжает
работать со старой версией файла, запечённой в образе при прошлой сборке.
Правка появлялась бы только после `docker compose up -d --build`.

Теперь это не нужно: шаблон можно полностью заменить **прямо из интерфейса**
(вкладка «Настройки» → «Шаблон документа») —

- **Скачать текущий шаблон** — открыть его в Word, отредактировать текст
  разделов, оформление и т.п. (плейсхолдеры `{{SIGN}}`, `{{VICE_HEAD}}`,
  `{{VICE_FIO}}`, `{{section1}}`…`{{section6}}` и структуру таблиц менять не
  надо — именно по ним программа находит, куда что подставлять);
- **Загрузить новый** — файл сначала проверяется пробной сборкой документа
  тестовыми данными; если чего-то не хватает (нужных таблиц или
  плейсхолдеров), загрузка отклоняется с объяснением, а старый шаблон
  продолжает работать как ни в чём не бывало;
- **Вернуть встроенный шаблон** — откатиться к тому, что идёт с программой
  по умолчанию.

Загруженный шаблон хранится как `custom_template.docx` в `DATA_DIR` (том с
данными) — переживает `docker compose down`, обновление кода и пересборку
образа, и правки вступают в силу сразу, без каких-либо перезапусков.

## Настройка нейросетей (список моделей)

Зайдите на вкладку **«Настройки»**. Там уже есть 6 заготовок популярных
сервисов (выключены — впишите свой ключ/адрес и включите):

| Заготовка | Что нужно | Где получить |
|---|---|---|
| **OpenRouter (DeepSeek)** | API-ключ | https://openrouter.ai/keys — есть бесплатные модели с пометкой `:free` |
| **Groq (Llama 3.3)** | API-ключ | https://console.groq.com/keys — щедрый бесплатный лимит |
| **Google Gemini** | API-ключ | https://aistudio.google.com/apikey — бесплатный лимит запросов |
| **DeepSeek напрямую** | API-ключ (платно) | https://platform.deepseek.com/api_keys — свой API DeepSeek, без посредников, `base_url = https://api.deepseek.com` |
| **Ollama** | ничего (локально) | https://ollama.com — `ollama pull llama3.1` |
| **LM Studio** | ничего (локально) | https://lmstudio.ai — загрузите модель, откройте вкладку «Developer» → «Start Server» (по умолчанию `http://localhost:1234/v1`); точный id модели удобнее всего выбрать кнопкой «🔍 Каталог» (см. ниже) |

DeepSeek и LM Studio технически ничем не отличаются от остальных — у них тот
же тип API `openai_compat` (OpenAI-совместимый), что и у OpenRouter/Groq/
Together, просто со своим адресом. Никакого отдельного кода под них не
понадобилось — это и есть смысл универсального типа провайдера.

Кнопкой **«+ Добавить модель»** можно завести сколько угодно ещё — любой
OpenAI-совместимый сервис (Together, Fireworks, свой vLLM-сервер и т.п.),
платную модель, вторую модель того же сервиса и так далее. У каждой модели
задаётся:

- **тип API** — `openai_compat` (большинство сервисов), `gemini` или `ollama`;
- **приоритет** — чем меньше число, тем раньше эта модель пробуется при
  автопереключении;
- **платная/бесплатная** — просто для собственной пометки в списке;
- кнопка **«проверить»** — шлёт тестовый запрос и показывает бейджем,
  отвечает ли модель прямо сейчас, с текстом ошибки при сбое.

На вкладке «Новое предложение» в выпадающем списке по умолчанию стоит
**«Автоматически (по приоритету)»** — так и рекомендуется оставлять, чтобы
работал автоматический переход между моделями. Можно и явно выбрать одну
конкретную модель — тогда генерация начнёт именно с неё, а если она
откажет, всё равно попробует остальные включённые по приоритету.

### Как работает автопереключение

При генерации бэкенд идёт по включённым моделям в порядке приоритета. Если
модель вернула ошибку — HTTP 429 (лимит исчерпан), неверный ключ, недоступный
адрес, что угодно — попытка фиксируется и программа переходит к следующей.
Это продолжается, пока одна из моделей не ответит успешно, либо пока не
закончатся все включённые модели (тогда возвращается ошибка со сводкой,
что именно не сработало у каждой). В интерфейсе после генерации видно,
какая модель сработала и что было испробовано до неё — если было
переключение, это будет явно написано под текстом.

## Как пользоваться

1. **Авторы** — один раз занесите людей, которые обычно участвуют в
   рацпредложениях (звание, ФИО, должность, место службы).
2. **Новое предложение**:
   - опишите тему/идею своими словами → «Сгенерировать текст»
     (по умолчанию — автоматический перебор нейросетей);
   - при необходимости отредактируйте наименование и текст любого из 6 разделов;
   - в блоке «Графическое изображение предложения» нейросеть предложит только
     короткую подпись/пояснение — сам чертёж/фото нужно будет вставить в
     готовый `.docx` вручную, это осознанное ограничение (нейросеть не рисует
     инженерные схемы);
   - выберите 6 авторов из базы (поиск по ФИО) и задайте проценты (сумма
     должна быть равна 100);
   - нажмите «Собрать документ» и скачайте готовый `.docx`.
3. **История** — все ранее собранные документы можно скачать повторно.

## Как добавить новый тип API (не через интерфейс, а на уровне кода)

Список моделей (провайдер, ключ, base_url, приоритет) целиком настраивается
через интерфейс — код трогать не нужно. Код нужно менять, только если
появляется сервис с принципиально другим протоколом (не OpenAI-совместимый
`/chat/completions`, не Gemini, не Ollama). Тогда в `backend/llm_providers.py`
создайте класс-наследник `BaseDriver` с методом `chat(system, user) -> str`
и добавьте его в словарь `DRIVERS` — новый `provider_type` сразу появится
в форме добавления модели на вкладке «Настройки».

## Экспорт/импорт авторов

На вкладке «Авторы» — кнопки «Скачать .csv» и «Загрузить из файла». Формат —
обычный CSV с русскими заголовками (Звание, ФИО, Должность, Место службы),
с BOM для корректного открытия в Excel на Windows. Импорт понимает и запятую,
и точку с запятой как разделитель (Excel в русской локали часто использует
именно точку с запятой). Загрузка не затирает базу целиком: авторы с уже
существующим ФИО обновляются, новые — добавляются, дубликаты не создаются.
Удобно и для резервных копий, и для переноса базы на другой сервер.

## Подписанты (ФИО)

Поле «ФИО подписанта» на вкладке «Новое предложение» (блок 6) работает так
же, как поле «Автор» в блоке 4: можно печатать напрямую (подсказки
появляются по мере ввода), выбрать из выпадающего списка или открыть кнопкой
«☰» полное модальное окно с поиском по всем сохранённым ФИО — там же можно
и удалить ненужную запись. В отличие от авторов, выбор **не обязателен**:
это просто текст, вставляемый в документ, а не связанные структурированные
данные, так что можно вписать и совсем новое имя, не сохраняя его заранее.
Управлять сохранённым списком (добавлять/удалять) можно централизованно на
вкладке «Настройки» — карточка «Подписанты (ФИО)».

## Журнал событий модели

Клик «изменить» у любой модели открывает модальное окно с формой настроек
**и журналом** всех проверок и попыток генерации по этой модели — с точным
текстом ответа сервера (не общей фразой «ошибка», а тем, что реально
прислал провайдер: HTTP-код, причина, при сбое разбора ответа — фрагмент
самого ответа модели). Это отдельная история на каждую модель, не
перезаписывается при следующей проверке (в отличие от бейджа «Статус» в
таблице, который показывает только последний результат) — полезно, когда
модель то работает, то нет, и непонятно почему: вся картина видна сразу,
можно пролистать назад кнопкой «Показать ещё». Журнал хранит последние 200
записей на модель и его можно отдельно очистить — полный ответ хранится в
той же строке БД, что и запись журнала (не отдельным файлом на диске), так
что очистка сразу делает недоступным и скачивание: обращение к уже
удалённой записи вернёт 404, а не осиротевший файл. Хранимый полный ответ
обрезается на ~1 МБ текста (с пометкой об этом), чтобы одна «сорвавшаяся»
модель (например, `base_url`, указывающий по ошибке не на API, а на обычный
сайт) не раздувала базу гигантскими сохранёнными ответами.

## Каталог моделей

В окне «Новая модель» / «изменить» рядом с полем «Модель» есть кнопка
**«🔍 Каталог»**. Она открывает второе окно со списком моделей выбранного
провайдера: поиск по названию/id, фильтр «Все / Только бесплатные / Только
платные» (где цена известна по каждой модели) и сортировка. Клик по строке
сам заполняет форму — тип API, адрес, точный id модели (без опечаток),
название, галочку «Платная» и рекомендуемый «Максимум токенов ответа».
Остаётся вписать API-ключ, если провайдер его требует.

| Провайдер | Ключ для списка | Что показывает |
|---|---|---|
| **OpenRouter** | не обязателен | Сотни моделей: контекст, макс. длина ответа, цена за 1 млн токенов или «бесплатно», **популярность** (только с ключом, см. ниже), пометки «рассуждающая» и «снимается с …» |
| **Together AI** | нужен | Модели с **ценой по каждой** (за 1 млн токенов), есть бесплатные (`…-Free`) |
| **Groq** | нужен | Модели с контекстом и макс. длиной ответа; тариф — бесплатный с лимитами |
| **Google Gemini** | нужен | Модели Gemini и Gemma с лимитами; «думающие» помечены как рассуждающие |
| **Mistral** | нужен | Модели с контекстом, псевдонимами (`…-latest`) и датой снятия с поддержки |
| **DeepSeek** | нужен | Модели с контекстом и макс. длиной ответа; платно |
| **Cerebras** | нужен | Список моделей; тариф — бесплатный с лимитами |
| **Ollama** | — | Модели, реально скачанные на этот Ollama: размер, параметры, квантование |
| **LM Studio** | — | Модели на сервере LM Studio: архитектура, квантование, загружена ли сейчас, контекст |
| **Другой OpenAI-совместимый** | если сервер требует | Любой адрес вида `…/v1` (OpenAI, Fireworks, Hugging Face, свой vLLM) — только id моделей |

В каталог включены только провайдеры, модели которых программа реально
умеет запускать: Gemini — через свой драйвер, все остальные облачные —
через OpenAI-совместимый `/chat/completions` (совместимость проверена по
документации каждого провайдера). Модели, которые не пишут текст в чате
(распознавание и синтез речи, картинки, эмбеддинги, модерация), из списков
убраны. Цены по каждой модели в API отдают только OpenRouter и Together — у
остальных в столбце «Тариф» показан тариф провайдера в целом, а фильтр по
цене отключён. Популярность из всех этих API отдаёт только OpenRouter.

Ключ для получения списка берётся из поля «API-ключ» формы (сохранять
модель заранее не нужно) или из уже сохранённой модели того же провайдера
и в браузер не передаётся. Если ключа нет, каталог сразу скажет, где его
получить. Некоторые провайдеры недоступны из части стран — тогда каталог
так и напишет «отказал в доступе по региону», а не «неверный ключ».

Особенности:

- **Популярность у OpenRouter требует ключа.** По документации OpenRouter
  умеет сортировать список по популярности, но без ключа молча игнорирует
  сортировку (проверено на живом API). Программа не верит сортировке вслепую:
  она проверяет, применил ли её сервер, и если нет — так и пишет «популярность
  недоступна без ключа», а не выдаёт случайный порядок за популярный. Ключ
  берётся из любой уже сохранённой модели OpenRouter (или из поля формы,
  если вы его только что вписали) и в браузер не передаётся — список
  запрашивает сервер программы.
- **Рассуждающие модели** (GPT-OSS, DeepSeek-R1 и т.п.) помечены отдельно, и
  для них сразу предлагается «Максимум токенов ответа» 8000 вместо 4000:
  часть лимита у них уходит на внутренние рассуждения, из-за чего раньше
  обрезались ответы. Значение не превышает того, что модель вообще умеет выдать.
- Модели, которые уже есть в вашем списке нейросетей, помечены «✓ уже добавлена».
- Список OpenRouter кэшируется на час, локальные — на 30 секунд; кнопка
  «⟳ Обновить» загружает список заново.
- **Docker и локальные модели.** Внутри контейнера `localhost` — это сам
  контейнер, а не ваш компьютер. Если программа запущена в Docker, а Ollama /
  LM Studio — на том же компьютере, укажите адрес через `host.docker.internal`:
  `http://host.docker.internal:11434` для Ollama и
  `http://host.docker.internal:1234/v1` для LM Studio. В `docker-compose.yml` для
  этого добавлена строка `extra_hosts` — без неё этот адрес не работает на
  Linux; на Windows/macOS он работает и так. Если подключение всё равно не
  проходит (чаще всего на Linux), значит Ollama / LM Studio принимают
  подключения только с самого компьютера: для Ollama задайте переменную
  окружения `OLLAMA_HOST=0.0.0.0` и перезапустите его, в LM Studio включите в
  настройках сервера «Serve on Local Network». Если подключиться не удалось,
  окно каталога само подскажет адрес через `host.docker.internal`.

## Статистика по моделям

На вкладке «Настройки» над таблицей моделей — сводная табличка: сколько раз
каждая модель успешно/неуспешно использовалась при генерации и при ручных
проверках, и процент успеха. Это тот же журнал событий, но в сводном виде —
не нужно открывать карточку каждой модели по одной, чтобы понять, какая из
них реально работает лучше, и куда имеет смысл подвинуть приоритет.

## Выбор конкретной модели vs «Автоматически»

Если в выпадающем списке «Нейросеть» выбрана **конкретная** модель — используется
только она, без переключения на другие при ошибке. Цепочка автопереключения
между несколькими нейросетями работает только при выборе **«Автоматически
(по приоритету)»**. Это специально сделано так после реального сценария:
человек выбрал одну модель, она не справилась, а программа тем не менее
попробовала ещё три другие подряд, незапланированно расходуя их лимиты.

## Обрезка ответа по max_tokens — теперь отдельная понятная ошибка

Если модель не успела дописать ответ в отведённый лимит токенов, провайдер
сообщает об этом явно (`finish_reason: "length"` у OpenAI-совместимых API,
`done_reason: "length"` у Ollama, `finishReason: "MAX_TOKENS"` у Gemini) —
программа теперь это проверяет и сразу пишет «ответ обрезан по достижении
лимита max_tokens», а не сбивающее с толку «не найден JSON-объект» (хотя
формально это тоже верно — объект просто не был закрыт). Особенно актуально
для рассуждающих моделей (GPT-OSS, QwQ, o-серия) — они тратят часть лимита
на внутренние рассуждения ещё до начала самого ответа, так что для них
обычно нужен запас заметно больше обычного (проверено на `openai/gpt-oss-120b`
через Groq).

## Автоматическое исправление обрезки по max_tokens

Если ответ модели обрезался, не дойдя до конца (`finish_reason: "length"` у
OpenAI-совместимых API, `done_reason: "length"` у Ollama, `finishReason:
"MAX_TOKENS"` у Gemini) — программа не просто сообщает об этом, а **сама
повторяет запрос к той же модели с увеличенным лимитом** (примерно в 2, затем
в 4 раза от заданного значения, с потолком в 32000 токенов), прежде чем
переходить к следующей модели в цепочке. Если один из повторов удался, новый
рабочий лимит **запоминается** в настройках этой модели — при следующей
генерации она сразу начнёт с него, без повторной эскалации. В прогресс-баре
это видно как «Ответ обрезан лимитом токенов — пробуем снова с увеличенным
лимитом (~N)...», а в финальном статусе — прямое указание, что лимит был
поднят автоматически. В журнале модели сохраняется каждый шаг эскалации
отдельной записью (с полным ответом, если он был).

Если модель отклонила запрос по совсем другой причине (не обрезка) —
эскалация не запускается, ошибка сразу считается финальной для этой модели.

**А если сам провайдер откажет с ошибкой «запрошенный max_tokens слишком
большой»** (у модели есть собственный потолок ниже, чем наш следующий шаг
эскалации)? Это не то же самое, что обрезка, и раньше в этом случае
программа сразу сдавалась на этой модели, хотя чуть меньшее значение вполне
могло сработать. Теперь код разбирает текст ошибки провайдера (большинство
называют точное число: «must be at most 8192» и подобные формулировки),
и если предел удалось распознать — пробует **именно его** следующим шагом,
вместо того чтобы просто увеличивать дальше или сразу переключаться на
другую модель. Если провайдер не назвал точное число или дошли до предела и
он всё равно обрезается — тогда действительно сдаётся и идёт к следующей
модели в цепочке, без зацикливания.

## HTTP 401 vs 403 — это разные ошибки

401 значит «ключ неверный/отсутствует» — это действительно проблема с
ключом. 403 значит «доступ запрещён» и может вообще не быть связан с
ключом: у Groq, например, модель может быть явно заблокирована в настройках
аккаунта (Model Permissions → console.groq.com/settings/limits), даже если
ключ абсолютно рабочий. Программа теперь различает эти коды и, если тело
ответа провайдера указывает на конкретную известную причину (блокировка
модели, ограничение по региону), пишет её прямо в сообщении — вместо общего
«неверный ключ» для обоих кодов, как было раньше. Плюс ко всем исходящим
запросам добавлен настоящий `User-Agent` — некоторые провайдеры за
Cloudflare блокируют запросы с дефолтным `User-Agent` голых HTTP-библиотек
как похожие на бота, что выглядело как ошибка ключа, хотя ей не являлось.

## Полный ответ модели в журнале, а не обрезанный

Раньше при ошибке разбора ответа (например, модель вернула повреждённый или
неполный JSON) в журнале сохранялся только обрезанный до ~300 символов
фрагмент — часто обрывавшийся на середине предложения и бесполезный для
диагностики. Теперь сообщение в журнале короткое и по делу («В ответе
модели не найден JSON-объект»), а **весь** ответ провайдера, без обрезки,
сохраняется отдельно и доступен по ссылке «⬇ полный ответ» под записью —
скачивается как обычный `.txt`-файл прямо из модального окна модели.

## Остановка генерации на лету

Кнопка «Сгенерировать текст» во время генерации превращается в «⏹ Остановить
генерацию». Это не просто разрыв соединения в браузере — отмена долетает и
до бэкенда: перебор моделей в цепочке автопереключения останавливается
**перед следующей попыткой**, чтобы случайная/неудачная генерация не сожгла
лимит сразу нескольких нейросетей подряд, пока вы не видите прогресс и
хотите поменять тему или параметры.

Технически: уже отправленный конкретной модели запрос долетит до конца
(простой HTTP-клиент не умеет прерывать соединение на лету) — но это только
одна попытка, а не вся оставшаяся цепочка. Флаг отмены хранится в общей БД
(не в памяти процесса), поэтому работает корректно и при нескольких
gunicorn-воркерах.

## Очистка текста перед документом

Текст разделов (и сгенерированный, и вставленный вручную) перед сборкой
документа проходит очистку (`backend/text_clean.py`):

- каждая строка — отдельный абзац с красной строкой. Раньше абзацы,
  разделённые одним переводом строки (так отвечают многие модели), сливались
  в один абзац с принудительными разрывами, и Word растягивал строки по ширине;
- остатки разметки markdown убираются: `### Заголовок` → «Заголовок»,
  `**жирный**` → «жирный», `- пункт` → «– пункт»;
- невидимые служебные символы (например, разрыв страницы из текста,
  скопированного из PDF) удаляются. Раньше из-за них сборка документа падала.

Нормальный текст (абзацы через пустую строку, без разметки) не меняется ни
на символ: документ из него получается побайтно тем же, что и до очистки.
Это проверено сравнением с эталонными документами.

Разбор ответа модели тоже стал устойчивее: блок рассуждений `<think>…</think>`
(DeepSeek-R1, Qwen3 и другие) пропускается, а пояснения модели до и после
JSON и настоящие переводы строк внутри текста больше не ломают разбор.
Наименование «способ …» со строчной буквы получает заглавную, а не
превращается в «Способ способ …».

## Заметки о производительности и надёжности

- У каждой модели есть своё поле **«Максимум токенов ответа»** (по умолчанию
  4000) — раньше `max_tokens` не передавался вообще, а у многих бесплатных
  моделей в этом случае действует скромный дефолт самого провайдера, из-за
  которого текст 6 разделов мог обрываться. Если конкретная модель отклоняет
  запрос как «слишком много токенов» — значение можно уменьшить точечно
  именно у неё, не трогая остальные модели.
- Для Ollama это особенно важно: без явного `num_predict` она по умолчанию
  обрезает ответ на **128 токенах** — теперь программа всегда передаёт
  разумное значение, даже если поле не заполнено.

- Проверка модели («проверить» / «Пинг всех») использует короткий таймаут
  (20 сек), в отличие от полной генерации документа (90 сек) — зависшая
  модель больше не держит кнопку почти полторы минуты.
- SQLite работает в режиме WAL (`journal_mode=WAL`) — меньше блокировок при
  параллельных запросах, если запущено несколько gunicorn-воркеров.
- Список истории («вкладка История») не парсит JSON разделов/авторов на
  каждую запись — эти поля там всё равно не показываются.
- При сборке документа нельзя выбрать одного и того же автора на две и
  более позиций — проверяется перед отправкой на сервер.
- **(Аудит 2026-10-03)** Обращения к нейросетям переведены с синхронного
  `urllib` на `httpx.AsyncClient`, а сами роуты генерации — на `async def`.
  Раньше один долгий перебор моделей (до ~90 сек на попытку, с эскалацией и
  несколькими моделями в цепочке) держал занятым целый поток воркера
  gunicorn, из-за чего при малом `WEB_CONCURRENCY` могли подвисать вообще все
  остальные запросы к приложению (проверка моделей, работа с авторами) —
  теперь ожидание ответа провайдера не блокирует обработку остальных
  запросов. Формат запросов/ответов к каждому провайдеру не менялся.
- **(Аудит 2026-10-03)** `max_tokens` у модели теперь не может быть меньше
  256 (проверяется на уровне формы и API) — раньше значение `0` тихо
  отключало ограничение вовсе (разная логика у разных протоколов не
  трогалась, фикс только на границе ввода).
- **(Аудит 2026-10-03)** `POST /api/models/check-all` больше не падает целиком,
  если при параллельной записи результата одной из моделей в SQLite
  случится редкая блокировка — остальные модели в пачке проверяются как
  обычно.

## Важные ограничения

- Тексты, которые пишет нейросеть, нужно проверять перед подачей — это
  черновик по вашей теме, а не гарантированно точное техническое описание.
  Не указывайте в теме реальные секретные сведения.
- Раздел «Графическое изображение предложения» нейросеть не иллюстрирует —
  чертёж/фото/схему нужно вставить в скачанный `.docx` вручную.
- Бланк подготовлен под конкретную форму Ф. № БИ-7 (6 авторов, 6 строк
  таблицы) — если у вас другое количество соавторов, потребуется небольшая
  доработка `docx_builder.py`.
